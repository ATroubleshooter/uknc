# gfour — графика и клавиатура

Три цветных квадрата прыгают по чёрному экрану 320×288, пока не нажата любая
клавиша (или пока не вышел предел кадров — чтобы прогон без человека
когда-нибудь закончился). Пример с настоящей графикой и настоящим вводом с
клавиатуры; `sin` устроен по его образцу и берёт его же ПП-часть.

## Сборка и запуск

```bash
make                            # gfour.sav, gfppu.ppu и gfour.dsk
make gfour.elf                  # с символами, для gdb (и gfppu.ppu.elf рядом)
```

Нужен образ примера — рядом с программой на нём лежит `GFPPU.PPU`:

```bash
../../debugger/bin/ukncbtldebug --disk1 gfour.dsk \
    --rom ../../rom/uknc_rom_autoboot.bin --boot --screen
```

и в RT-11 — `RUN GFOUR`. На диске `GFOUR.SAV`/`GFPPU.PPU`: `gfourppu` в шесть
символов RT-11 не укладывается.

Рядом с `Makefile` лежит `CMakeLists.txt` — тот же пример через CMake, с
ЦПУ- и ПП-частями сразу (`uknc_add_program` + `uknc_add_ppu_module`).

## Как это работает

Экран на УКНЦ строит видеогенератор по тег-листу в плане 0, а план 0
принадлежит ПП — поэтому тег-лист строит ПП-часть (`gfourppu.c`), а не
программа на ЦПУ. Пиксели же лежат в обычном буфере, который ЦПУ-часть
получила через `malloc`: вся память ЦПУ — это планы 1 и 2 вперемешку (байт 2N
— план 1, 2N+1 — план 2), а тег-лист может указать строку на любое смещение
плана, так что ПП достаточно сообщить адрес буфера, делённый на два. Он и
посылается, одним сообщением сразу после `ppuc_run()`.

Клавиатура — только у ПП (регистры 0177700/0177702, вектор прерывания 0300).
ПП-часть ставит свой обработчик и пересылает коды нажатий на ЦПУ каналом 1
(`ppus_send()` → `ppuc_recv_init()`); ЦПУ-часть ждёт первого настоящего
нажатия, а не отпускания. Канал 0, через который работает `.TTYIN`, для этого
не годится: как только тег-лист перехвачен, резидентный монитор ПП перестаёт
его обслуживать — по той же причине между `ppuc_run()` и возвратом управления
не работает и консольный вывод, поэтому все сообщения программа печатает до
`ppuc_run()`, и через `write()`, а не `printf`.

Выход устроен симметрично захвату: по первому нажатию ПП-часть пересылает
событие, восстанавливает тег 0, возвращает вектор 0300 монитору, снимает свой
приёмник канала 2, сообщает ЦПУ и выходит из `ppu_main()` — только после этого
консоль RT-11 действительно оживает. Если что-нибудь из этого пропустить,
машина остаётся с картинкой на экране и без обслуживания клавиатуры.

## В профиле

99.5% тактов ПП уходит в холостой цикл: ПП-часть построила тег-лист, подняла
клавиатуру и крутится в `for (;;)`, ожидая нажатия, — рисует здесь сам ЦПУ. У
ЦПУ своя половина той же картины: 37% времени в цикле ожидания кадра внутри
`wait_vsync`, дальше `fill_rect_px` — собственно отрисовка. Как снять такой
профиль и как перевести его в `.cpuprofile` для VS Code — в разделе про
профилировщик в README проекта.

## Где что написано

Подробности — в заголовках `gfour.c` и `gfourppu.c`: формат тег-листа,
палитра, что именно восстанавливается на выходе и почему. ПП-часть собирается
с `-Os`: загрузчик держит в памяти ЦПУ весь файл модуля плюс его разложенный
образ, так что размер ПП-программы ограничен не памятью ПП.
