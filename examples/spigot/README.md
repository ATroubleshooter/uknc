# spigot — цифры π

Считает десятичные цифры π «кранным» алгоритмом (spigot) — целочисленной
арифметикой, без плавающих, выдавая цифры порциями по четыре по мере
вычисления. Рабочая точность по умолчанию 3000, и цифр из неё выходит не
3000, а около `N·2/7` — 857: этот вариант алгоритма печатает четыре цифры на
каждые четырнадцать единиц точности. Точность можно передать параметром в
командной строке RT-11 (`RUN SPIGOT 500`) — её разбирает `parse_args` из
crt0, так что `argc`/`argv` в `main` настоящие.

## Сборка и запуск

```bash
make                            # spigot.sav и spigot.dsk
make spigot.elf
UKNC_FRAMES=15000 ../../gcc/dejagnu/uknc-run spigot.sav
```

Прогон длинный: 13 875 кадров, то есть 4 минуты 37 секунд машинного
времени, поэтому бюджета `uknc-run` по умолчанию — 3000 кадров — не хватает,
и его надо поднять.

## Что в нём смотреть

Это пример про память, а не про математику. Из 64 КБ адресного пространства
программа с массивом занимает 20 578 байт (это и есть высокий предел в слове
050 заголовка `.sav`), стек `crt0` ставит по ответу `.SETTOP` — на этой
машине 45 632, — и между ними остаётся около 25 КБ на стек и кучу.

Отсюда три решения, которые видно в исходнике:

- `r[]` — `static`, то есть в `.bss`, а не на стеке. Разница не в скорости, а
  в том, кто за размер отвечает: в `.bss` массив входит в память образа, его
  считает слово 050, и программа, которая не влезет, скажет об этом при
  загрузке. На стеке те же 6 КБ брались бы из зазора между `_end` и верхом
  стека молча, без защитной страницы, и переполнение затирало бы код самой
  программы;
- вывод идёт через `fputs` и собственный `ltoa`, а не через `printf`: на этой
  цели `printf` всегда тянет за собой `dtoa`/`mprec` — машинерию
  форматирования плавающих, — потому что `_printf_float` должен был бы быть
  слабым символом, а pdp11-бэкенд gcc слабых объявлений не поддерживает, и
  ссылка остаётся сильной независимо от того, встречается ли в программе
  `%f`;
- `setvbuf(stdout, NULL, _IONBF, 0)`: иначе первый же вывод выделит под буфер
  `BUFSIZ` — ещё 1024 байта, которые этой программе ни к чему.

И ещё одно, уже про библиотеку: половина такт этого прогона — 51% —
приходится на деление из libgcc, потому что вся программа состоит из `d % b`
и `d /= b` над `long`. То есть это ещё и мерило целочисленного деления (см.
`tests/pdp11-fis`).
